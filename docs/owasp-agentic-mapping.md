# Offline OWASP Agentic Mapping

This additive command-line tool relates a small subset of existing observations to
**OWASP Top 10 for Agentic Applications 2026**. It is not the LLM Applications Top 10,
a new scanner, a compliance assessment or a change to the frozen experiment.

The implementation is `tools/owasp_agentic_mapping.py`. It runs separately from the
frozen `agentsec-evidence` entry point and uses no Docker engine, network requests,
model calls or target execution. Original HTML, JSON, SARIF, native findings, review
proposals and scanner rules remain unchanged.

## Initial Relationships

The registry is [owasp-agentic-2026-mapping-v1.json](../profiles/owasp-agentic-2026-mapping-v1.json).
Its three relationships are AI-drafted project interpretations, **not independently
reviewed mappings**. Approval to implement this feature does not approve each mapping
or establish that an observation is a vulnerability.

| Rule | Category | Relationship and boundary |
|---|---|---|
| TOOL-EXEC-004 | ASI05 | Conditional relevance: a direct tool-parameter reference at eval/exec. Actual registration, argument provenance, rebinding, validation, reachability and sandbox context require review. |
| MEM-SEC-107 | ASI01 | Conditional relevance: nonliteral system-message content. Trusted templates can match; lower-trust influence on real agent goals/actions is not established. |
| A2A-001 | ASI07 | Inventory context only: agent-like routing/call syntax. This does not establish an actual agent exchange, missing authentication or insecure communication. |

These are rule-level relationships, not mappings of whole families. In particular,
memory-named rules do not automatically demonstrate ASI06, and self-modification
syntax does not demonstrate ASI10. All other rules remain unmapped in this registry.
Native taxonomy tags exposed by the input projection are retained separately without
guessing their edition. Tags absent from those reports are not recovered or invented.

Each relationship binds the family, producer name, exact producer version, record
kind and complete native rule definition. A changed definition or version produces an
explicit unmapped result instead of silently inheriting the old interpretation.
Deferred rules cannot be promoted to condition mappings. An inventory relationship
cannot become a finding relationship.

## Inputs and Outputs

Supported input: one sealed **`corpus-core-report-v2`** directory generated by
`tools/corpus_report_v2.py`, plus an external manifest hash and registry hash. The tool
checks manifest membership, file hashes and lossless v2 reconstruction. It does not
replay native scanner execution or independently attest the source measurements.

Other common-report, original v1 and repository-rehearsal contracts are not accepted.
For Qdrant, use the retained corpus R02 report, not the later standalone demo report.

The fresh output folder contains:

- `README.md`: ten-category overview and interpretation limits.
- `mapping.json`: repository/revision, all execution cells, category summaries and
  observed custom catalog entries with mapping/unmapped status, including deferred IDs.
- `cells/*.json`: separate observed tool/view/repetition/batch records, condition vs
  inventory type, native record identity/hash/pointer, source location, native policy,
  proposed relationship, rationale and required verification. Upstream tags stay opaque.
- `registry.json`: exact mapping registry bytes, source attribution and reference hash.
- `source-evidence-manifest.json`: the original report manifest, not the native reports.
- `provenance.json`: source/registry/tool/helper bindings and the zero-scan boundary.
- `evidence-manifest.json`: package file membership, lengths and SHA-256 hashes.

Files remain under the existing 16 MiB per-file and 128 MiB per-package budgets.
Output must be fresh and cannot overlap the source or registry. Inside this checkout,
only `outputs/` or `workspace/` destinations are allowed. Inputs and outputs reject
links/reparse points; retained files reject hard links. Partial output is not retried
or overwritten automatically: preserve it and choose another fresh destination.

Category summary counts use **repetition 1 only**. Every observed repetition and
policy view remains separate in the detail files. Unsupported/refused/failed/unrun
cells retain null counts and original reasons. Partial analysis remains explicit.
Observed custom inventory is counted separately; baseline inventory stays null because
these input projections do not provide it. Overlaps are not deduplicated
into claimed vulnerabilities. A catalog mapping does not establish that its rule ran
completely or produced any observation.

All ten categories retain `category_assessment: not-assessed`: the overlay does not
assess whole categories. `related_evidence` indicates conditional static relevance,
inventory-only context or no related records. Zero is not a passed check. The absence
of a mapped record can reflect limited mapping scope, analysis limits or ordinary
input, not security. There is no coverage percentage, overall risk score or compliance
claim. Original source snippets, full native records and contextual reviews remain
external; verification requires the original report and registry.

## PowerShell Usage

From the development checkout with its existing environment:

```powershell
$report = 'outputs\corpus_core_collection_2026-10-22\R11'
$registry = 'profiles\owasp-agentic-2026-mapping-v1.json'
$output = 'outputs\owasp-agentic-r11-example'
$reportHash = (Get-FileHash "$report\evidence-manifest.json" -Algorithm SHA256).Hash.ToLowerInvariant()
$registryHash = (Get-FileHash $registry -Algorithm SHA256).Hash.ToLowerInvariant()

.\.venv\Scripts\python.exe -B tools\owasp_agentic_mapping.py write `
  --report $report --report-sha256 $reportHash `
  --registry $registry --registry-sha256 $registryHash --output $output

.\.venv\Scripts\python.exe -B tools\owasp_agentic_mapping.py verify `
  --report $report --report-sha256 $reportHash `
  --registry $registry --registry-sha256 $registryHash --output $output
```

Obtain hashes from a previously verified, trusted local snapshot and retain them
outside the new package. Calculating a hash from arbitrary bytes does not establish
their authenticity. Verification reconstructs the expected mapping from the bound
source and registry and compares exact output bytes, including implementation/helper
provenance. Re-sealing an altered mapping cannot make it pass that comparison. A tool
revision requires a separate derived package; do not rewrite historical evidence.

Reports and target evidence are not distributed in Git. A fresh clone needs the
retained source package from its owner; this command is not an arbitrary-repository
scan. Output is internal/unredacted. Review paths, policy metadata, source rights and
distribution permissions before sharing it.

## Verification Boundary

Authored tests cover mapping/version binding, inventory separation, opaque native
tags and suppression metadata, repeat accounting, unknown execution states, changed
source/output packages, hash mismatches and path boundaries. Offline operation is
tested with subprocess and socket creation forbidden. These tests validate the
overlay, not detector accuracy or the correctness of the proposed taxonomy judgment.

Use the overlay alongside the retained HTML and contextual reviews. A native HTML
integration, broader registry or new detection coverage is outside this increment.
